Technology

Werkbot is a small system of cooperating agents. One reads the job, one prepares the documents, several drive hidden browsers in parallel, and a decision layer settles every answer or hands it to a person. This page describes how it is built and what is still planned.

01

The problem

Applying for a job is the same work, repeated. Every employer hosts its own form, often on a shared applicant tracking system, with its own fields, dropdowns, uploads and login walls. The same facts are typed again and again, and the same few questions come back in different words.

Automating it has a known failure. When a form asks something the tool cannot source, the tool guesses. A wrong answer about a work permit, a notice period or a salary is worse than an empty field, because the person only finds out after sending.

Werkbot is built around that failure. The agents do the typing and the reading. Every answer has a source, anything without one goes to the person, and only the person sends.

02

How one application runs

Each application is a single unit of work with a state. The same eight steps run for every one of them.

  1. IntakeResolves a pasted link or a feed job to the real application page and detects which form system it uses.
    In testing
  2. Prepare the kitTailors a one-page CV from the person's CV bank to the job text, and drafts a cover note when the form asks for one.
    In testing
  3. Read the formTakes the question list from a form system's public interface where one exists, and from the page structure in the browser otherwise.
    In testing
  4. AnswerThe decision layer settles every field with a source, or marks it as a question for the person.
    In testing
  5. FillA hidden browser types, picks dropdown values and uploads the CV, then reads every value back and fixes any mismatch.
    In testing
  6. Needs youThe run pauses on the field. The question appears in the side panel with its own reply box. The answer is saved and the fill continues.
    In testing
  7. Review and sendEvery answer is shown with its source, the CV and the note can be edited, and only a click sends.
    In testing
  8. Confirm, track, learnThe confirmation page marks the application as sent. Following the employer's later emails, and learning from what the person changed before sending, are planned.
    Planned

03

The agent stack

Six roles, each with one job and a narrow interface to the next. Keeping them separate means a model is only used where judgement is needed, and plain code does everything that must be exact.

Planner

Takes a link or a feed job, resolves the apply page, picks the adapter, schedules browser agents and owns the state of every application.

In testing

Form reader

Turns a page into a list of typed fields: text, dropdown, upload, consent. Cheapest source first, public question list before browser.

In testing

Kit agent

Writes the tailored CV and the cover note from the person's own material and the job text.

In testing

Browser agent

Drives one hidden browser session: fills, uploads, reads values back, streams frames to its tile and hands over on request.

In testing

Decision agent

Settles each answer from a source or raises a question. The next section describes its ladder.

In testing

Tracker

Reads the employer's confirmation and later emails and moves each application through sent, interview and rejected.

04

Agentic browsing and browser agents

Werkbot drives a real browser, not a back door. That is why it works on the form an employer actually shows, including uploads, custom dropdowns and conditional questions. The browser is hidden. It never takes the foreground of the person's machine, and it streams frames to a tile so the person can watch, or take over, at any moment.

A form is filled by three layers, cheapest and most predictable first.

Form system adapters

Deterministic code per applicant tracking system. Fast, no model in the loop, and predictable. Greenhouse first.

In testing

Learned label map

Same form system, new company: the agent remembers which label means which profile field, so the next company needs fewer questions.

Planned

General browser agent

A model looks at the page and acts, for sites without an adapter. A successful run is saved as a replayable script, so the next run on that site needs no model.

Planned

05

Agent orchestration

An application moves through a fixed set of states: queued, preparing, filling, needs you, ready for you, sending, sent, failed and withdrawn. The planner is the only component that changes a state, and it runs several browser agents at once, each in its own isolated session.

The parallel application grid shows all of them as tiles. Each tile carries a live frame of its browser, its state, how many fields are filled and the match ring for the job. A person can see five applications moving and step into whichever one has asked for help.

In testing

06

The decision layer

Every field is answered from the first rung of this ladder that has a source. The order is the point: exact data before remembered data, remembered data before drafted text, and a question before a guess.

  1. Profile factsName, email, phone, links, university and dates. Exact values, no model involved.
  2. Answer bankAnswers the person gave or edited before, matched by meaning, so two differently worded questions about weekly hours resolve to the same answer.
  3. Model draftOpen text only, such as motivation, written from the profile and the job and shown for review.
  4. Ask the personEverything else. Work permit, visa, salary, start date, diversity questions and legal consents are never filled without a source.

Each answer keeps its source, so the review screen can show where every value came from. The rule is designed as code in the pipeline rather than an instruction to a model: a field with no source is not filled.

In testing

07

Human handoff and learning

The agent is allowed to stop. Stopping well is a feature, because it turns a wrong guess into a one-line question.

Needs you

The tile changes state and the question appears in the side panel. Captchas and sign-in walls the agent cannot pass take the same path.

In testing

Take control

The person drives the hidden browser by hand, then gives it back. The agent carries on from the page the person left it on.

In testing

Remembering answers

An answer typed into the side panel is stored with its source and can be edited later, so the same question is not asked twice.

In testing

Learning from corrections

What the person changes between the draft and Send flows back into the answer bank, so each form asks less than the last.

08

Safety and control

Werkbot acts on a person's behalf, so the limits are part of the design. These guards are built and under test.

  • Send is a click. There is no automatic send. One send per application.
  • Checked before Send. The page is still the application form, no required field is empty, and every value reads back as expected.
  • Never guesses. A field with no source stays empty and becomes a question.
  • Hidden, not intrusive. Browsers run in the background and never take the foreground of the machine.
  • Personal data stays local. In the current version the CV bank, answers and contacts live in local files, outside any code repository.
